# Dify チャットフローの設定と注意

LLMノードのSYSTEMに貼る中身は [dify_llm_prompt.md](dify_llm_prompt.md)（ファイル全体をそのまま貼る）。このファイルは、その前提・入力変数・モデル設定・貼り方の注意をまとめたもの。

プロンプトは2026-09-28作成。`safety_guardrails.md`（見直し前の防災アシスタント向け）を、2026-09-25の見直し（ハザードマップとして扱う、「雨水のたまりやすさマップ」）と画面のJSON契約に合わせて書き直したもの。安全上のルールは `safety_guardrails.md` と `RAG/03_用語とデータの説明.md` の「回答のルール」から引き継いでいる。2026-09-30に、注意書きをこのファイルに分けた。

## アプリの構成

開始 → 知識検索（`naisui-knowledge`） → LLM → 回答

- 知識検索のクエリは `sys.query`。バックエンドが質問の前に町丁目名を付けて送る（例: `中延六丁目について: 水はたまりやすい？`）ので、町丁目のファイルが検索に掛かる。このマップそのものや用語の意味を聞く質問では `このマップについて: 使い方は？` のように送り、`RAG/04_このマップについて.md` と `RAG/03_用語とデータの説明.md` が検索に掛かるようにする（2026-09-30）。
- LLMノードの「コンテキスト」に知識検索の結果を設定する。
- 構造化出力（JSONスキーマ）が使えるモデルなら有効にする。使えなくても、バックエンドが契約を検証し、違反時はテンプレート応答に戻す。
- モデル: Gemini 3.8 Flash（有料枠）。Include thoughts・Grounding・URL context はFalse（考えた過程や検索結果を混ぜない）、Thinking level Low、Output length 4096、Temperature 0.2。無料枠は1日20回・1分5回で、Difyが429のたびに呼び直すため試験ですぐ尽きる（2026-09-28）。
- Difyの無料プランには、ナレッジの検索回数に1分あたりの上限がある。続けて10回ほど呼ぶと `you have reached the knowledge base request rate limit of your subscription`（HTTP 400）になり、バックエンドはテンプレート応答に戻る。試験は間をあけて行う（2026-09-28）。

## 開始ノードの入力変数

バックエンドがAPIの `inputs` で渡す（`backend/app/llm_adapter.py`）。緊急ワード・200字を超える質問・判断を求める質問（避難の要否・経路・通行・安全）・今の状況や予報を聞く質問・範囲外・特定できない場所・複数の町丁目は、バックエンドがDifyを呼ぶ前に判定済み（`backend/app/policy.py`）。SYSTEMの同じルールは、言葉の判定を擦り抜けた質問への備え（2026-09-29追加）。

| 変数 | 型 | 例 | このマップ・用語の質問のとき |
| --- | --- | --- | --- |
| `town_name` | 短文 | 中延六丁目 | `このマップ全般（町丁目の指定なし）` |
| `scenario_label` | 短文 | 想定最大規模降雨 (1時間153mm・24時間690mm) | 同じ |
| `calibration_status` | 短文 | pre_calibration_screening | 同じ |
| `risk_level` | 短文 | 要注意 | `対象外（町丁目の指定なし）` |
| `area_ratio_pct` | 短文 | 12.34 | `対象外` |
| `official_status` | 段落 | `{"source": "品川区（未接続）", "evacuation_notice": null, "weather_warning": null, "shelter_status": "unknown", "road_status": "unknown"}` | 同じ |

このマップそのもの（目的・使い方・地図の見方・計算のしかた・技術など）や、用語の意味（「暗渠って何？」など）を聞く質問で、町丁目名が書かれていないときは、町丁目を選んでいなくてもDifyを呼ぶ（2026-09-30追加、`policy.detect_about_map`）。入力変数は増やさず、`town_name` の値でプロンプトの答え方を切り替える（プロンプトの「答え方」2行目）。

## SYSTEMの貼り方

- [dify_llm_prompt.md](dify_llm_prompt.md) の変数は、Difyの内部の書き方（`{{#1790583408474.town_name#}}`）で書いてある。`1790583408474` は開始ノードのID。別のアプリに作り直したときは、IDを合わせるか、Difyのプロンプト欄で `/` または `{` を押して変数を入れ直す。
- 貼ったあと、変数が `ユーザー入力 / town_name` のような札（チップ）になっていることを確認する（開始ノードは画面では「ユーザー入力」と表示される）。挿入のために打った `{` が札の前に残らないようにする（2026-09-30、`{{{#…#}}` と括弧が3つになっていた）。
- `{{#context#}}` はコンテキスト（知識検索の結果）。
- 直したら「公開する」→「更新」。APIは公開済みの版で動く（2026-09-28、下書きだけ直して例の値のまま動いていた）。
- 確かめ方: 目印の値（例: `area_ratio_pct` に `7.77`）をAPIで送り、「このアプリが渡すデータの6行をそのまま写して」と頼む。

## バックエンド側で行うこと

- `sources` はLLMに作らせず、バックエンドが付ける（モデル、公式情報、`naisui-knowledge`）。
- `prohibited_claim_check` のいずれかが true、必須項目の欠け、`status` が上の4つ以外、タイムアウトのときは、テンプレート応答に戻す。
- 命に関わる状況の案内は、バックエンドの緊急ワードの判定（`policy.detect_emergency`）で行う。SYSTEMには入れていない（2026-09-30、ユーザー決定）。

## Difyのナレッジとリポジトリの差

- 2026-09-30に、リポジトリの `RAG/02_町丁目_*.md`（10件）と `RAG/03_用語とデータの説明.md` から「校正前」を外した（モデルは校正しない方針）。Difyのナレッジは入れ替えておらず、古い版（「校正前の試算」と書かれた版）のまま。
- そのため、プロンプトの「答え方」に「ナレッジに『校正前』と書かれていても、回答では書かない」の1行を足している。次にナレッジを入れ替えるときに、この1行は外してよい。
- `RAG/04_このマップについて.md` は2026-09-30に追加済み。その後、見出しのリンク名を「このマップについて知る」に変えた（リポジトリは直した、Difyは入れ替えていないので「このマップについて」のまま）。
