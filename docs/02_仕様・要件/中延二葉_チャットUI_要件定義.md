# 中延・二葉 内水氾濫AI/GIS PoC — チャット＋地図UI 要件定義

最終更新: 2026-09-15
対象: 中延・二葉 内水氾濫AI/GIS PoCの、上司・同僚向けデモUI（フロントエンド＋バックエンド）
前提ドキュメント: `docs/02_仕様・要件/UI_デザイン受け入れ基準.md`（本書とあわせて改訂）、`docs/02_仕様・要件/中延二葉_段階3_Dify_LLM安全ガードレール仕様.md`、`docs/00_現状・引継ぎ/中延二葉_PoC_引継ぎ・タスクリスト.md`

## 1. 作るもの / 作らないもの

### 作るもの

- **共通**: Difyが返す説明（選択した町丁目ベースの内水氾濫の状態・状況・想定・近くの土のう置場）をチャットで提示する
- **共通**: 対象町丁目の選択はフリーテキストではなく、既存データがある10町丁目からの**ボタン選択式**（PC・モバイル共通、モバイルでも「あわてて打たなくてよい」選択方式とする）
- **モバイル（〜1023px想定）**: 地図なし。緊急時の避難相談を想定し、チャットのみで完結するUI
- **PC（1024px〜、1920×1080基準）**: 操作可能な内水氾濫ハザード地図（MapLibre GL JS）とチャットの2列構成。地図レイヤーは①ハザードオーバーレイ（校正前スクリーニング結果）②**土のう置場マーカー**③**避難所マーカー**の3層。チャット列はノートPCで画面のおよそ3分の1を目安とし、最小360px・最大520pxに制限する。大画面では地図列だけを拡張し、チャット列を不必要に広げない
- QGIS成果物（ベクタ/ラスタ）をWeb地図用形式へ変換するエクスポートタスク一式（実施済み）
- 土のう置場データ（`sandbag_locations_ebara.csv`、住所のみ）と避難所データ（品川区防災ポータルの公式一覧から中延・二葉エリア5件）を、それぞれ緯度経度へジオコーディングしGeoJSON化するエクスポートタスク（実施済み）
- FastAPI (Python) バックエンド: GIS照会（`risk_lookup_*.json`/`scenario_summary.json`をメモリキャッシュ）、決定的ポリシー判定、LLM呼び出し（Dify未接続の間の暫定アダプタ）、出力検査
- シナリオは区の想定最大規模降雨（`sc_153mmh_24h_690mm_official`、1時間153mm・24時間690mm）に固定する。時間分布は正式ハイエトグラフ入手までの暫定配分であることを根拠表示に含める
- 公式情報の暫定表示（手動更新JSON、既定値`unknown`）
- GitHub (`https://github.com/junhongo-ccs/naisui`) 経由で Vercel（フロント）+ Render（バックエンド）へデプロイ
- `.env`によるシークレット管理、`.gitignore`で大容量データ・`__pycache__`等を除外

### 作らないもの

- Dify側ワークフローの構築（別作業。今回はバックエンド側にロジックを実装し、後で差し替え可能なアダプタを用意するに留める）
- 公式情報の実API連携（現状APIが存在しないため）
- アクセス制御（パスワード保護なし、と合意済み。共有範囲は上司・同僚のみという運用ルールで担保する）
- ベクタタイル化・専用タイルサーバーの構築（対象範囲が中延・二葉に限定されるためオーバースペック）
- 段階2c（下水道管網等の高度化水理モデル）
- 中延・二葉以外のエリア（荏原・立会川等）のデータ整備。想定利用者像の描写としてのみ言及し、実際に選択できるのは既存10町丁目に限る

## 2. 主ユーザーと利用状況

- 上司・同僚が、会社支給ノートPC（1920×1080基準）またはスマートフォンでデモを閲覧・チャット操作する
- 想定ペルソナ（デモ上の描写）は中延・荏原・立会川周辺エリアの住民。ただし実際にデータがあり選択できるのは中延・二葉の既存10町丁目（`中延一〜六丁目`、`二葉一〜四丁目`）のみ
- モバイルの主な利用シーンは「緊急時の避難相談」であり、地図操作よりも即答性を優先する。町丁目選択もフリー入力ではなくボタン選択とし、あわてて文字入力する必要をなくす
- PCの利用シーンは、地図（ハザード＋土のう置場）を見ながらの詳細確認・説明用途を想定する
- 一般住民は対象外（安全ガードレール仕様の導入条件が未達のため）

## 3. 画面構成（テキストワイヤー）

```
PC (1920x1080基準、大画面では地図列のみ可変)
┌────────────────────────────────────────────────────┐
│ ヘッダー: 対象地域 / 公式情報確認リンク                           │
├──────────────────────────────────┬─────────────────┤
│ ハザード地図(操作可能、可変幅)          │ チャット(360〜520px) │
│ - ズーム/パン/凡例                     │ - 町丁目ボタン選択     │
│ - 校正前ステータス常時表示               │ - 質問と回答           │
│ - 土のう置場・避難所マーカー             │ - リスク要約・安全上の注意 │
│ - 町丁目ポリゴンクリック                 │ - 出典・不確実性       │
│   →チャット入力欄へ反映                 │ - 質問入力 + 送信      │
└────────────────────────────────────────────────────┘

モバイル(360px〜、地図なし)
┌──────────────────────────┐
│ ヘッダー: 対象地域              │
├──────────────────────────┤
│ 町丁目ボタン選択(10件)        │
│  ※フリー入力での代替も可      │
├──────────────────────────┤
│ チャット(全面)               │
│ - 質問と回答                 │
│ - リスク要約・安全上の注意      │
│ - 近くの土のう置場・避難所(テキスト+外部地図リンク)│
│ - 根拠カード(折りたたみ)       │
├──────────────────────────┤
│ 質問入力 + 送信              │
└──────────────────────────┘
```

避難所マーカー/情報は、品川区防災ポータルの公式一覧から中延・二葉エリア5件を特定しジオコーディング済み（2026-09-15）のため、上記ワイヤーに含めている。座標は住所代表点のジオコーディング結果であり、施設の正確な位置・リアルタイムの開設状況（品川区防災ポータルが持つ`開設中`/`閉鎖中`等のライブ情報）は未連携。ライブ状況の取り込みは別タスク。

## 4. 状態一覧

| 状態 | 挙動 |
|---|---|
| 初期表示 | 想定最大規模降雨シナリオを固定し、町丁目未選択。PCは地図＋町丁目ボタン、モバイルは町丁目ボタン＋チャット初期案内を表示 |
| 町丁目選択 | ボタン選択（10町丁目）または地図クリック（PCのみ）で入力欄に反映。送信は明示的なボタン操作で行い、選択だけでは自動送信しない |
| ローディング | 送信不可＋スピナー。既出のチャット履歴・入力欄は保持する |
| エラー | 再試行導線を表示。既出履歴は消さない |
| 空/根拠不足 | 該当町丁目データが無い場合、根拠不足を表示し町丁目名の再確認を促す |
| 緊急検知 | 切迫ワード入力時、分析説明を打ち切り緊急対応の定型案内へ切替 |
| PC/モバイル切替（リサイズ） | ブレークポイント（1024px）をまたぐ場合、地図関連コードの読み込み/破棄を伴うコンポーネント切替を行う |
| PC地図列のリサイズ | `ResizeObserver`でMapLibreのコンテナ寸法を検知し、選択中の町丁目があれば現在の地図幅で境界への`fitBounds`を再実行する。ノートPC・大画面・外部ディスプレイで選択地点が中心からずれないようにする |

## 5. 技術前提

| 項目 | 内容 |
|---|---|
| フロントエンド | React + Vite + Tailwind CSS。地図は **MapLibre GL JS**（PCのみ動的import、モバイルはバンドルに含めない） |
| バックエンド | FastAPI (Python) + uv。既存の`tools/`のPython資産を再利用 |
| Dify接続 | 未実装。バックエンドにLLM呼び出しのアダプタ層を用意し、将来Dify APIへ差し替え可能にする |
| QGIS成果物のWeb化 | 実施済み（2026-09-15）。`tools/export_web_hazard_layer.py`が`hazard_shinagawa_normalized.gpkg`をEPSG:4326のGeoJSONへ変換し`depth_class`ごとの色を`color`プロパティに埋め込む（→`data/naisui_poc/02_processed/web_map/hazard_pdf_derived.geojson`、2,486件）。`tools/export_web_ponding_overlay.py`が`pysheds_surface_routing`の`maximum_ponding_depth_m.tif`（50/80/100mm）を着色PNG＋MapLibre `ImageSource`用bounds JSONに変換する（→`ponding_depth_<scenario_id>.png`/`.bounds.json`）。配色はPDF由来レイヤー（黄〜赤）と区別できるよう独自の青系グラデーションとし、両者が同一データに見えないようにしている。変換はビルド時/データ更新時に一度だけ行い、都度変換しない |
| 土のう置場データ | 実施済み（2026-09-15）。`tools/geocode_sandbag_locations.py`が国土地理院住所検索APIで`sandbag_locations_ebara.csv`（8件、住所のみ）をジオコーディングし、`data/naisui_poc/01_raw/shelter/sandbag_locations_nakanobu_futaba.csv`/`.geojson`を生成済み。住所代表点であり施設の正確な設置位置ではない旨を列に明記。実行時に都度ジオコーディングしない |
| 避難所データ | 実施済み（2026-09-15）。品川区防災ポータル（`bosai.city.shinagawa.tokyo.jp`、公式一覧53施設）から中延・二葉エリア5件（中延小学校、源氏前小学校、上神明小学校、豊葉の杜学園、延山小学校）を特定し、国土地理院住所検索APIでジオコーディング（→`data/naisui_poc/01_raw/shelter/shelter_locations_nakanobu_futaba.csv`/`.geojson`）。住所代表点であり施設の正確な位置ではない。品川区が持つリアルタイム開設状況（`shelter_status`）は未連携で、当面`unknown`表示とする |
| 公式情報 | 手動更新可能な設定JSON、既定`unknown` |
| リポジトリ構成 | モノレポ（`frontend/`, `backend/`を新設）。既存`data/`, `tools/`, `docs/`は維持 |
| デプロイ | GitHub (`junhongo-ccs/naisui`) → Vercel（フロント）/ Render（バックエンド） |
| シークレット管理 | `.env`（コミットしない）＋`.env.example` |
| `.gitignore` | GeoTIFF等の大容量ラスタ、`__pycache__`、`.env`等を除外 |
| アクセス制御 | なし（合意済み） |

## 6. 制約（安全）

- PC地図の凡例に「校正前のスクリーニング結果」を常時表示する
- モバイル・PC共通で、LLMは公式の警報・避難情報より優先されない
- 個別の避難先・経路・浸水の確定値を断定しない
- 応答は次のJSON契約に従う: `headline / status / facts / model_context / safe_next_steps / prohibited_claim_check / sources`
- LLM呼び出し前に決定的ポリシー判定を実施する（公式情報優先、校正前は数値予報禁止、避難所未確認は利用不可と断定しない、切迫時は緊急対応の定型文へ切替、位置曖昧なら町丁目確認を一度だけ行う）

### モデルと浸水実績データの提示方針

（`docs/03_モデル検証/中延二葉_モデル実績照合レビュー.md`のレビューでは「実績を主、モデルを補助」が提案されたが、ユーザーの判断により以下の方針を正とする。2026-09-15）

- **回答の主はモデル推定**（シナリオ別のリスク推定・危険度）とする。区の浸水実績はモデルを補助・検証する根拠情報として併記する。実績データは過去のイベントの記録であり、未経験の降雨シナリオや面的な傾向を予測できないため、PoCの目的（シナリオベースのスクリーニング）に対してはモデルが主たる回答を担う
- 実績データは「このモデルが過去の浸水傾向とどれだけ整合しているか」を示す検証材料として、根拠パネル・回答の出典欄に含める（例:「このモデルの町丁目別リスク順位は、過去31年間の浸水実績との相関がρ=+0.62（80mmシナリオ、参考値）」）。相関値はシナリオ依存（80mm: ρ=+0.62、100mm: ρ=+0.52、50mm: 算出不能）であり、n=9のため80mm以外は統計的有意水準に達していない。詳細は`docs/03_モデル検証/中延二葉_モデル実績照合レビュー.md`第2章
- モデルの継続的な改善（実績との乖離を減らす校正）は`docs/03_モデル検証/中延二葉_モデル実績照合レビュー.md`の優先度A/Bタスクに従って進める。UIはこの校正が未完了である前提（校正前ステータス表示）を維持したまま成立させる

## 7. 検収チェックリスト

- [ ] 幅360pxで送信・閲覧・根拠表示が横スクロールなしで完結する（モバイル）
- [ ] チャット本文15px以上、背景`#FAFAFA`+teal系キーカラー
- [ ] PC（1024px以上）でハザード地図が操作可能、モバイル（1023px以下）では地図コードが読み込まれない
- [ ] PC地図の町丁目クリックはチャット入力欄への反映のみで、自動送信はしない
- [ ] PC・モバイルともに10町丁目からのボタン選択で町丁目を指定でき、自由入力なしでも操作を完結できる
- [ ] PC地図に土のう置場マーカーと避難所マーカーが表示される（避難所の開設状況は当面「未確認」表示）
- [ ] PC地図の凡例に校正前ステータスが常時表示される
- [ ] PCは地図とチャットの2列構成で、右端の状態・根拠ペインが表示されない
- [ ] PCチャット列は最小360px・最大520pxで、ノートPCでは画面のおよそ3分の1に収まる。1920×1080以上では地図列だけが拡張される
- [ ] ノートPC・大画面・外部ディスプレイで地図列の幅が変わっても、選択中の町丁目へ`fitBounds`を再実行し、中心位置がずれない
- [ ] 同一シナリオでの再質問・再表示時に再フェッチ・白画面化が発生しない
- [ ] 区の想定最大規模降雨（1時間153mm・24時間690mm）が唯一のシナリオとして表示され、旧50/80/100mm/hの選択肢・切替UIが表示されない
- [ ] QGIS由来のベクタ/ラスタ、および土のう置場データがビルド時にGeoJSON/着色PNGへ変換済みで、実行時に都度変換されない
- [ ] 回答に計算対象時刻・シナリオ・公式情報確認導線がある
- [ ] 公式情報未取得時は「未確認」表示で断定しない
- [ ] 切迫ワード入力で緊急対応の定型案内に切替
- [ ] `.env`・GeoTIFF等がgit管理外である
- [ ] フロントがVercel、バックエンドがRenderに、`junhongo-ccs/naisui`経由でデプロイされている

## 8. 未確定の前提（推測で埋めた箇所）

- 緊急ワード検知ロジックは初版では簡易キーワードマッチとし、精緻化は後日行う
- Dify未接続の間のLLM呼び出し先（Anthropic API直呼び出しか固定テンプレート応答か）は実装時に確認する
- Renderの無料プランはコールドスタート/スリープの可能性があり、デモ直前に手動アクセスして起こす運用が必要になり得る
- 避難所のリアルタイム開設状況（品川区防災ポータルの`開設中`/`閉鎖中`等）の取り込み方法は未定。当面は`shelter_status: unknown`固定とし、別タスクとする
